# Claude Usage and Value Dashboard: data model and data dictionary

Star schema: 1 dimension (users), 1 benchmark lookup table, 3 facts. There is no date table: each fact carries its calendar date directly. All data in `data/` is synthetic, generated by `generate_data.py` (seed 42), and shaped to match Claude's real admin data.

- Period: 1 January to 30 September 2026 (273 days)
- Organisation: 60 users, 4 sub-teams, 4 roles
- Licence price assumed: USD 20 per user per month, plus usage billed per token
- People who left during the period are kept for the months they held a licence

Column names such as `has_seat` and `seat_cost_usd` keep the source systems' wording. In reports and definitions these are called licences.

## Relationships

| From (many) | To (one) | Key |
|---|---|---|
| `fact_usage_daily` | `dim_user` | `user_key` |
| `fact_cost_daily` | `dim_user` | `user_key` |
| `fact_edit_decision_daily` | `dim_user` | `user_key` |

`dim_role_benchmark` has no direct relationship. A benchmark is looked up by the user's role and the fact's date: the row whose `role` matches `dim_user[role]` and whose `quarter_start` to `quarter_end` contains the date.

## Dimensions

### dim_user (60 rows): one row per team member

| Column | Type | Description | Real source |
|---|---|---|---|
| `user_key` | INT, PK | Surrogate key | Generated |
| `email` | VARCHAR | Work email; join key to all Claude data | HR system, matched to `user.email_address` |
| `claude_user_id` | VARCHAR | Claude's own user identifier | Analytics API `user.id` |
| `full_name` | VARCHAR | Display name | HR system |
| `team` | VARCHAR | Customer, Finance or Operations Analytics, or Data Platform | HR system |
| `role` | VARCHAR | Business Analyst, Data Analyst, Data Engineer, Project Manager | HR system |
| `start_date` | DATE (dd-mm-yyyy) | Date the person joined the company | HR system |
| `seat_assigned_date` | DATE (dd-mm-yyyy) | Date the Claude licence was assigned | Identity provider or Claude admin export |
| `end_date` | DATE (dd-mm-yyyy), nullable | Leaving date; blank if still employed | HR system |
| `is_active` | BOOLEAN | False for leavers. Reflects status today, not on a given date | HR system |

## Dates

Every date in every file uses the **dd-mm-yyyy** format (for example `24-01-2026`): the `date` column on each fact, the user dates in `dim_user`, and the quarter and window dates in `dim_role_benchmark`. A blank `end_date` means the person has not left.

The CSVs store dates as text. Load them as dates with a day-first format (Power Query: type date with culture `en-GB`; Tableau: date format `dd-MM-yyyy`). Loaded as plain text they sort wrongly, by day first.

Month, quarter and week are derived from `date` in the report. Weekends and holidays are no longer flagged in the data; 1 January 2026 was the only holiday in the period.

## Engagement scoring rules

There is no feature table: `fact_usage_daily` carries each activity's name in `feature_name`. These rules are applied when the points are calculated and are kept here as documentation.

Scoring rule: `engagement_points = MIN( CEILING(interaction_count ÷ count per unit) × weight, daily cap )`

| Feature name | Analytics API field | Category | Weight | Counted as | Daily cap (points) |
|---|---|---|---|---|---|
| Chat messages | `chat_metrics.message_count` | Basic prompt | 1 | 1 unit per 2 messages | 10 |
| Files uploaded | `chat_metrics.distinct_files_uploaded_count` | Summarise / extract | 2 | Each file | None |
| Web searches | `web_search_count` | Summarise / extract | 2 | Each search | 10 |
| Artifacts created | `chat_metrics.distinct_artifacts_created_count` | Generate | 3 | Each artifact | None |
| Office add-in messages | `office_metrics.excel.message_count` + `office_metrics.powerpoint.message_count` | Generate | 3 | 1 unit per 2 messages | 9 |
| Projects used | `chat_metrics.distinct_projects_used_count` | Advanced / agentic | 4 | Each distinct project | None |
| Connector calls | `chat_metrics.connectors_used_count` | Advanced / agentic | 4 | Each call | 12 |
| Claude Code sessions | `claude_code_metrics.core_metrics.distinct_session_count` | Advanced / agentic | 4 | Each session | None |
| Cowork sessions | `cowork_metrics.distinct_session_count` | Advanced / agentic | 4 | Each session | None |

## Benchmark lookup table

### dim_role_benchmark (16 rows): one row per role per quarter

Each quarter's benchmark is the median daily engagement score of active user-days in the previous three complete months, recalculated at each quarterly refresh. Q1 2026 has no earlier data, so it uses its own months. Q4 2026 is what the October refresh produces from July to September.

| Column | Type | Description |
|---|---|---|
| `benchmark_key` | VARCHAR, PK | Role and quarter, e.g. `Data Engineer|2026-Q3` |
| `role` | VARCHAR | Role name |
| `quarter` | VARCHAR | Quarter the benchmark applies to, e.g. 2026-Q3 |
| `quarter_start`, `quarter_end` | DATE (dd-mm-yyyy) | Dates the benchmark applies to |
| `window_start`, `window_end` | DATE (dd-mm-yyyy) | Months the benchmark was calculated from |
| `daily_benchmark` | INT | Median engagement points per active user-day in the window, rounded half up |
| `weekly_benchmark` | INT | Daily × 5 |
| `monthly_benchmark` | INT | Daily × 20 |

| Role | Q1 2026 (from Jan–Mar) | Q2 2026 (from Jan–Mar) | Q3 2026 (from Apr–Jun) | Q4 2026 (from Jul–Sep) |
|---|---|---|---|---|
| Data Engineer | 19 | 19 | 18 | 19 |
| Data Analyst | 14 | 14 | 14 | 14 |
| Business Analyst | 11 | 11 | 11 | 12 |
| Project Manager | 8 | 8 | 8 | 8 |

## Assumptions

These values are fixed assumptions for the project. They are applied in the report measures and are not stored in the data model.

| Assumption | Value |
|---|---|
| Active user threshold | 5 or more active days in the month |
| User segments | Idle = no activity in the month; Light = below 50% of the role's monthly benchmark; Regular = 50% to 150%; Power = above 150% |
| Idle licence | Licence held at the end of the range, with no activity in the last two months of the range |
| Benchmark multipliers | Weekly = daily × 5; monthly = daily × 20 |
| Benchmark refresh | Quarterly, from the previous three complete months |
| Licence price | USD 20 per user per month, plus usage billed per token |
| Adoption target | None |

## Facts

### fact_usage_daily (19,768 rows): user × feature × day

Real source: Claude Enterprise Analytics API, `GET /v1/organizations/analytics/users?date=`, one call per day, each metric unpivoted to a row. Rows exist only where the count is above zero.

| Column | Type | Description |
|---|---|---|
| `date` | DATE (dd-mm-yyyy) | Day of activity |
| `user_key` | INT, FK | Who |
| `feature_name` | VARCHAR | Which activity, e.g. Chat messages; one of the nine names in the scoring rules |
| `interaction_count` | INT | Raw value of that metric for the day |
| `engagement_points` | INT | Scored value after scaling and capping |

### fact_cost_daily (16,380 rows): user × day, every user and every day

| Column | Type | Description | Real source |
|---|---|---|---|
| `date` | DATE (dd-mm-yyyy) | Day | Derived |
| `user_key` | INT, FK | Who | Derived |
| `has_seat` | BOOLEAN | Held a Claude licence that day | Identity provider or admin export |
| `seat_cost_usd` | DECIMAL | Licence cost: monthly licence price ÷ days in month; 0 without a licence | Contract |
| `usage_cost_usd` | DECIMAL | Token consumption cost that day | Analytics API per-user cost report (cents, converted) |
| `total_cost_usd` | DECIMAL | Licence + usage | Derived |

### fact_edit_decision_daily (27,214 rows): user × edit tool × language × decision source × day

Real source: Claude Code OpenTelemetry metric `claude_code.code_edit_tool.decision`, aggregated per day.

| Column | Type | Description | Source attribute |
|---|---|---|---|
| `date` | DATE (dd-mm-yyyy) | Day | Timestamp |
| `user_key` | INT, FK | Who | `user.email` |
| `edit_tool` | VARCHAR | Edit, Write or NotebookEdit | `tool_name` |
| `language` | VARCHAR | Language of the edited file; `unknown` for unrecognised extensions | `language` |
| `decision_source` | VARCHAR | `config`, `hook`, `user_permanent`, `user_temporary`, `user_abort`, `user_reject` | `source` |
| `is_user_decision` | BOOLEAN | True for the four `user_*` sources | Derived |
| `accepted_count` | INT | Suggestions approved | `decision = accept` |
| `rejected_count` | INT | Suggestions declined | `decision = reject` |

## KPI formulas

Active users, adoption, segments and the headline figures are monthly measures.

| KPI | Formula |
|---|---|
| Licensed users | Distinct `user_key` in `fact_cost_daily` where `has_seat` on any day of the month |
| Active day | A day with at least one row in `fact_usage_daily` for the user |
| Active users | Distinct users with 5 or more active days in the month |
| Adoption rate | Active users ÷ licensed users × 100, per month |
| Usage frequency | Active days per active user per month |
| Engagement score | SUM(`engagement_points`) |
| % of benchmark | Monthly engagement score ÷ `monthly_benchmark` for the user's role and the month's quarter |
| Meeting benchmark | Active users with % of benchmark ≥ 100% ÷ active users |
| User segment | Idle if score = 0; Light if below 50%; Regular if 50% to 150%; Power if above 150% |
| Licence cost | SUM(`seat_cost_usd`) |
| Total cost | SUM(`total_cost_usd`) |
| Cost per active user | Total cost in the month ÷ active users in the month |
| Idle licence | Licence held at range end and no usage in the last two months of the range |
| Days idle | Range end − last active date, or range end − licence assigned date + 1 if never used |
| Idle-licence cost | Licence cost of idle licences |
| Acceptance rate | SUM(`accepted_count`) ÷ SUM(accepted + rejected), where `is_user_decision` |
| Explicit rejection rate | SUM(`rejected_count`) where `decision_source = user_reject` ÷ all user decisions |
| Auto-approval share | Decisions where `decision_source` is `config` or `hook` ÷ all decisions |

## Patterns built into the data

- Staggered rollout: Data Platform on 5 Jan, Customer and Finance on 19 Jan, Operations on 2 Feb.
- Four new joiners (April to July) and two leavers (Tomas Darwish on 30 Jun, Lina Farouk on 14 Aug).
- Five user types: power, regular, light, churned (stop between mid-April and June) and never-activated.
- Weekend activity is rare; August dips for leave.
- Claude Code is used by all 18 data engineers, 10 of 20 data analysts, 4 of 14 business analysts and 3 of 8 project managers.
- Three project managers build prototypes and small tools with Claude Code (Python, JavaScript, TypeScript). They run with 84% of edits auto-approved, the highest of any role. A fourth is a regular chat-only user.
- Acceptance improves over time (about 76% in January to 85% in September) and varies by language (Markdown highest, Shell lowest).
- A quarter of Claude Code users run with mostly automatic approvals, which is why the all-decisions rate overstates acceptance.
